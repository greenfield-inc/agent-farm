Summary

The browser's dark preference and the existing colour tokens were already there; PR #42 adds a stored choice, a tiny script that applies it before paint, dark token values, and a Settings control that writes the choice.

Iceberg

understoodpartlymissed or hotspotnot touched

Decisions behind it: D-1 (segmented control) and D-2 (device storage). Hotspot: the boot script, where review found F-1.

Deep dive

Boot script (P-1) partly

Plain words A few lines in the page head read the saved theme and set data-theme on the root element before the browser paints anything.

How it connects index.html:12-24 sets the attribute; src/styles/tokens.css:40 swaps token values on [data-theme="dark"].

Trade-offs It must stay tiny and dependency-free, so it duplicates the store's parsing in a few lines.

What to watch Any storage call can throw (F-1). Keep the try/catch when editing it.

Theme store (P-1) understood

Plain words One module owns the saved choice: read it, write it, and tell listeners when it changes.

How it connects src/theme/store.ts; the Settings control calls setTheme.

What to watch The device-preference listener only runs while System is chosen (F-2).

Appearance control (P-2) understood

Plain words Three buttons in a group; the selected one gets the accent fill and a check mark.

In this codebase It reuses src/ui/ButtonGroup.tsx, which already handles arrow keys.

Device colour preference partly

Plain words The browser reports whether the device is in dark mode, and tells the page when that changes.

Where it lives The prefers-color-scheme media query, read through matchMedia.
