Plan: share a note with teammates ready-for-review

A Jotter user shares a note with people in their workspace, who can view or edit it from "Shared with me"; the owner can change or remove access at any time, and every shared note shows who last edited it.

In three sentences

We let a note's owner share it with workspace members as a viewer or an editor (SC-1), list the notes shared with a user in a new "Shared with me" view (SC-2), and let the owner change or remove access, effective on the next read (SC-3). The server stores each share in a new table and checks it on every read and save of a note the user does not own, and each note records who last edited it (SC-4). Teammates can work on the same note without copying and pasting it.

Before and after

Before

Every note is private to its owner. The only way to give a teammate a note is to copy its text. Captures: current app.

After

A Share button on each note opens the approved dialog; the sidebar gains "Shared with me". Screens that must match (5 frames, desktop and phone, light and dark): dialog, added, manage, list, empty.

What we're building

Three things a user can do, each shown with its approved mockups (desktop, light; click a frame to open it). Open a track's sections for what happens step by step, the rules, and what makes it work underneath: the packages that build it and the database changes it needs, linked to their rows in Schema changes.

  1. Share a note: pick teammates, choose view or edit
  2. Find notes shared with you: the new sidebar view and who last edited each note
  3. Change or remove access: takes effect on the next read

1 · Share a note

What happens, step by step
  1. The owner opens a note and chooses Share. The dialog lists workspace members as they type.
  2. They pick one or more people and set each to Can view or Can edit (view is the default).
  3. Share saves the access. The note appears in each person's Shared with me at once; nobody is emailed (D-5).
  4. Sharing the note again with someone who already has access changes their access instead of adding them twice.
Rules

SC-1 · D-1, D-2, D-5

Only the owner shares. Access is view or edit, nothing else (D-1). Only members of the same workspace can be picked; there are no public links (D-2).

What makes it work underneath

P-1 adds the share routes and stores each share in note_shares, one row per person per note. P-3 builds the dialog from the existing member picker and Modal.

2 · Find notes shared with you

What happens, step by step
  1. The sidebar gains Shared with me under My notes.
  2. It lists every note shared with the user, newest share first, with the owner, the access they have, and "Last edited by … · time".
  3. Opening a note with view access shows it read-only; with edit access, the editor works as on their own notes.
  4. Long titles are cut with an ellipsis on one line; the empty state says nothing has been shared yet.
Rules

SC-2, SC-4 · D-1

A user sees only notes shared with them. "Last edited by" shows on every shared note, for owners too.

What makes it work underneath

P-2 adds the shared-notes query, served by the per-user index, and writes last_edited_by and last_edited_at on every save, with a backfill for existing notes. P-3 builds the view from the existing note list.

3 · Change or remove access

What happens, step by step
  1. The owner opens Share; People with access lists everyone with their access.
  2. Changing someone to Can view stops their edits from their next save; Remove access takes the note out of their Shared with me.
  3. Someone who has the note open when access is removed sees "You no longer have access" on their next save or reload; nothing they typed after removal is saved.
Rules

SC-3 · D-4

Only the owner changes or removes access. Removal is immediate on the server; there is no grace period (D-4).

What makes it work underneath

P-1 updates or deletes the note_shares row, and its access check runs on every read and save of a note the user does not own, so a change applies on the next request. P-3 adds the menu to the dialog.

Schema changes

Every database change this feature makes, as one migration in server/db/migrations/: 4 statements in two groups, applied in order S1 then S2, plus one backfill. It all adds; nothing is dropped or renamed. Each group shows its exact DDL, then what each object is for and why it is needed. The badge says who is affected if it is missing when the new server starts: everyone, one feature or slower / minor.

New tables

S1. note_shares: who can view or edit a note (2 statements)

P-1, P-2 · SC-1, SC-2, SC-3 · D-1, D-2

CREATE TABLE note_shares
(
    note_id    UUID        NOT NULL REFERENCES notes (id) ON DELETE CASCADE,
    user_id    UUID        NOT NULL REFERENCES users (id) ON DELETE CASCADE,
    access     TEXT        NOT NULL CHECK (access IN ('view', 'edit')),
    shared_by  UUID        NOT NULL REFERENCES users (id),
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (note_id, user_id)
);

CREATE INDEX note_shares_user_created_idx ON note_shares (user_id, created_at DESC);
ObjectWhat it is forWhy it's needed
note_sharesOne row per person a note is shared with: their access, who shared it and when. Shown in the dialog's People with access.everyone Notes have a single owner column today, so there is nowhere to say who else may read or edit one. Every read of a note the user does not own checks this table, so if it is missing when the new server starts, those reads fail.
note_shares_user_created_idxEvery note shared with one user, newest first.slower / minor Serves Shared with me. Without it, the list scans every share in the database.

Fast: a new, empty table and its index; nothing to backfill.

Changes to existing tables

S2. notes: who last edited each note (2 statements)

P-2 · SC-4

ALTER TABLE notes ADD COLUMN last_edited_by UUID REFERENCES users (id);
ALTER TABLE notes ADD COLUMN last_edited_at TIMESTAMPTZ;
ObjectWhat it is forWhy it's needed
notes.last_edited_by, last_edited_atWho saved the note last, and when. Shown as "Last edited by" in Shared with me and on the note.everyone Once a note has several editors, updated_at no longer says who changed it. Every save writes both columns, so if they are missing when the new server starts, every save fails.
Backfill (not DDL)Sets both columns on existing notes from owner_id and updated_at. Re-runnable; fills only empty values.slower / minor Without it, existing notes show "Last edited by —" until their next save.

Fast: two nullable columns, nothing filled by the database. Run the backfill after the server is live, so no save falls in a gap; it needs the person's approval on staging and production.

Considered and not needed

  • An access column on notes. One note has many people with different access, so it needs its own table.
  • A share history table. Nothing asks for a history of shares yet; shared_by and created_at say who shared and when.

How it rolls out

  1. Staging: the implementer raises a needs_you with the migration; the person approves, then it is applied with pnpm db:migrate --env staging.
  2. Production: the server pull request's Deploy notes carry the same migration. A human applies it before the server deploys. No agent runs production migrations.
  3. Backfill: after the server is live, with the person's approval on each environment.
  4. Rollback: revert the code. The additive schema stays; the new table and columns sit unused.

Approach, reuse, and affected areas

Reuse: the workspace membership check on the member picker route; the route and test helpers in server/routes/.

New: the share routes and the access function. No new dependency.

Schema and data: S1, note_shares.

Scope

Constraints

No change to how notes are saved beyond the last-edited columns. No new browser dependency. Production migrations are applied by a human.

Non-goals

Public links, comments, live co-editing, sharing folders, transferring ownership.

Ask-first actions
