Decision 1: one file per note, or one file for everything picked A · D-1

Decision drivers

  1. Each note stays usable on its own in another editor (SC-1, SC-2).
  2. File names never collide (SC-3).
  3. Fits one day of work.

How others do it

n/a because this choice turned on our own data shape and the drivers above; no product research was needed for a one-day appetite.

Option A: one .md per note; "export all" bundles them in a .zip

Optimizes
Each note is a file you can open, move or share alone.
Gives up
"Export all" is a zip, one extra step to open.
Risk and reversibility
Low. Adding a combined file later is additive.
Ladder rung
3: a new export module; the zip uses the archive library the server already has.
Complexity
One serializer, one file-name function, two routes.
Requirement trade-offs
Meets SC-1, SC-2 and SC-3 directly.
Migration cost
None. Storage is unchanged.
How we'd verify
Download one note and all notes; open the files; compare with the app.
Mockup and journey
n/a because the UI change is one menu item and one button in existing places.

Option B: one combined .md with every note under its own heading

Optimizes
One file, no zip.
Gives up
Notes are not separate; moving to a tool with one file per note means splitting by hand.
Risk and reversibility
Low, but headings inside notes clash with the per-note headings.
Ladder rung
3: a new export module.
Complexity
Slightly less than A: no zip.
Requirement trade-offs
Fails SC-2's "one file per note".
Migration cost
None.
How we'd verify
Export, then count notes in the file.
Mockup and journey
n/a, as for A.

Option C: a format picker (Markdown, combined Markdown, JSON)

Optimizes
Covers every use, including machine backups.
Gives up
Three formats to test and keep working; a picker to design.
Risk and reversibility
Medium. Formats, once shipped, are hard to remove.
Ladder rung
3, with three times the surface.
Complexity
Well over the one-day appetite.
Requirement trade-offs
Meets all criteria and adds unasked-for formats.
Migration cost
None.
How we'd verify
Each format, each scope.
Mockup and journey
Would need a picker mockup.

Smallest version

Single-note download only. Meets SC-1 and SC-3; misses SC-2.

Do nothing

Users keep copying and pasting. Checklists keep losing their ticks.

Recommendation

Option A. It is the only option that meets every criterion inside the appetite.

What you accept

"Export all" arrives as a zip, not a folder.

Confirmation

The QA journeys open the downloaded files and find one file per note with distinct names.

Blocking unknowns

None.

Decision 2: where the Markdown is built picked A · D-2

Decision drivers

  1. One serializer for both buttons, so single and bulk files match (SC-3).
  2. Testable without a browser.
  3. "Export all" must not need every note loaded in the page.

How others do it

n/a because this is an internal choice, not an interface decision.

Option A: a server endpoint

Optimizes
One code path; unit tests cover it; the server already has every note.
Gives up
A request per export.
Risk and reversibility
Low. Two read-only routes behind the existing owner check.
Ladder rung
2 for the routes, 3 for the serializer module.
Complexity
Two routes, owner check reused.
Requirement trade-offs
None found.
Migration cost
None.
How we'd verify
A server test suite plus the app journeys.
Mockup and journey
n/a.

Option B: in the browser

Optimizes
No server change for a single note.
Gives up
"Export all" must fetch every note into the page first; a second zip library ships to every visitor.
Risk and reversibility
Low, but tests need a browser.
Ladder rung
4: a new browser dependency.
Complexity
Similar code, harder to test.
Requirement trade-offs
Strains driver 3.
Migration cost
None.
How we'd verify
App journeys only.
Mockup and journey
n/a.

Smallest version

Server endpoint for a single note only.

Do nothing

n/a because decision 1 already chose to build an export.

Recommendation

Option A, the server endpoint.

What you accept

A short wait while the server builds the zip.

Confirmation

The server suite covers the serializer and file names; the app journeys show both buttons produce the same name for the same note.

Blocking unknowns

None.

Socrates verdict

Fast pass, one question. "Is a zip really needed, or would single-note download be enough?" Answer: SC-2 came from users with dozens of notes; one-at-a-time download repeats today's pain. Verdict: proceed with A and A.

What we learned

  • Checklist ticks live in a flag, so any export has to write "- [x]" itself. See the explainer.
  • Titles are not unique, which makes the file-name rule a real requirement (SC-3), not polish.
